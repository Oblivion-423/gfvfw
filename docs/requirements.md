## 0. 一句话定位

一个面向 **Falcon BMS** 虚拟飞行联队的、**公开前台 + 分权限成员后台**的网站，
核心价值是：**把散落在各人手里的 Tacview 录制文件，自动变成可查、可统计、可公示的联队战史。**

### 1.1 ACMI 提取指标（六类中，五项入库，一项取消）

1. 飞行时长、起降次数、总航程
2. 机型、呼号、参战名单
3. 武器投放（发射 / 投弹 / 命中事件）
4. 击落 / 被击落 / 战损
5. 超限与事故（过载、超速、撞地、坠毁）
6. ~~编队轨迹地图回放（网页内可视化）~~ → ❌ **明确不做（用户决定）**

### 1.2 视频回放明确排除 ✅（本轮决定）

**不做网页轨迹回放。网站的职责边界是：接收 ACMI 文件 → 解析 → 记录结构化数据。**

| 项 | 决定 |
|---|---|
| 上传 ACMI 原件 | ✅ 做（归档保存，供下载） |
| 解析并记录数据 | ✅ 做（时长、名单、武器、战损、超限等） |
| 网页内地图/轨迹回放 | ❌ **不做** |
| 看回放的方式 | 成员下载 ACMI 原件，用**本地 Tacview** 打开 |

**这条决定消除的成本**（原计划中技术风险最高的部分）：

| 被消除的工作 | 原风险 |
|---|---|
| 服务端轨迹降采样管线（1~2 Hz） | R1 |
| 轨迹数据切片与分页传输接口 | R1 |
| 前端地图库集成与坐标系转换（经纬度 ↔ 战区坐标） | R1 |
| 浏览器端动画/时间轴渲染引擎 | R1 |
| 为 21 MB 单文件设计的分块流式加载 | R1 |

⚠️ **但上传体积约束依然存在**：ACMI 原件仍要上传与归档，
实测单文件最大 **21 MB**（197 文件 / 总计 1301 MB），
因此上传环节仍需支持大文件与合理超时策略 —— 只是**不再需要为"播放"做任何优化**。

## 2. 内容可见性三层模型 ✅

贯穿**所有实体**的一个字段（`visibility`），而非靠"页面藏起来"。

| 层级 | 谁能看 | 典型内容 |
|---|---|---|
| `public` 公开 | 任何人（含未登录访客、**游客**、搜索引擎） | 首页概览、注册页、公告、战报精选、招新 |
| `members` 队内 | **队员**（`active`） | 详情页与写操作：任务详情与架次、ACMI 原件、战役态势、队内资料下载、Logbook 上传 |
| `command` 指挥层 | 管理员/联队指挥 | 战损、失误、处罚记录、真实姓名、联系方式、账号信息 |

> ⚠️ **实现现状（本轮）**：`visibility` 字段从建模起就铺在
> `Member` / `Campaign` / `Mission` / `Announcement` / `SiteEvent` /
> `ForumThread` / `Document` 上，但**Web 层此前完全没有落地**（等于全站
> "登录即可见"；实测全仓库**没有任何一处**查询用 `visibility` 过滤）。
> 本轮把**页面级**边界做实，并且**改了口径** ——
> 不再是"游客什么都看不见"，而是**列表/汇总页开放、详情页与写操作仅队员**：

| 页面 | 现在要求 | 说明 |
|---|---|---|
| `/`、`/login`、`/register` | **公开** | 未登录可开 |
| `/apply`、`/apply/status`、`/account` | 已登录（**游客也可**） | 注册与申请是两步，见 §4.7 |
| **列表 / 汇总页**：`/members`、`/campaigns`、`/theater`、`/missions`、`/log`、`/log/campaign`、`/log/training`、`/log/pilots`、`/stats`、`/library` | **已登录（游客可看）** | 呼号/军衔/飞行时长/统计排行/资料目录全部开放 |
| **详情页**：`/members/{id}`、`/campaigns/{id}`、`/missions/{id}`、`/theater/{id}` 及其 `/air` `/ground` `/map` `/objectives` `/timeline` `/saves`、`/sorties/{id}/edit`、Logbook | **队员** | 游客得到 403 **说明页**，见 §4.7 |
| 写操作：一切 `POST`（`/acmi/*`、`/members/new`、`/campaigns/*/edit`、`/theater/upload`、`/applications/*` …） | **按权限点（隐含队员）** | 游客权限点集合恒为空 |

> ⚠️ **列表页里的写操作 UI 必须一起挡住。** `/log/campaign` 与 `/log/training`
> 既是对游客开放的列表页，又内嵌了 **ACMI 工作台**（上传/认领/归并/删除）。
> 模板里以 `principal.is_member` 判定，游客拿到的 HTML 里**不含**这些表单 ——
> 否则游客会看到"上传 ACMI"的按钮，点了必然 403，属可见的误导。
> `tests/nav_selfcheck.py` 与 `tests/access_selfcheck.py` 都盯着这条。

**逐条记录的 `visibility`**（例如"哪几份资料对公开"）仍待落地 ——
`/library` 资料查询目前是占位页，见 §14 二期。

> ⚠️ 注意：`command` 层包含个人隐私数据（真实姓名、联系方式）。
> 需明确**是否收集**、**留存期限**、**成员能否要求删除**（见 §8 待定 Q7）。

## 3. 角色与权限 ✅（固定角色 + 预留扩展）

| 角色 | 说明 | 关键权限 |
|---|---|---|
| `owner` 超级管理员 | 系统所有者 | 全部权限、角色授予、系统配置、备份 |
| `commander` 联队指挥 | 联队管理层 | 全部业务权限、审批、发布公告、查看 command 层 |
| `instructor` 教官 | 训练与考核 | 录入考核结果、创建训练任务、审核日志 |
| `member` 成员（队员） | 普通队员 | 上传自己的 ACMI、编辑自己的架次、报名活动、发帖 |
| `visitor` 访客（游客） | **已注册但未入队** | 只读 `public` 内容（**各区块的列表与汇总**）+ 自己的申请进度 |

⚠️ 上表是**角色**（存表、可扩展）。与**三档身份**不是一回事，别混淆：

* `visitor` 角色是"零权限预设"，但**不入库为角色分配** ——
  游客的判定看 `users.status == 'pending'`，不看角色（见 §4.7）。
  这么定是因为一个未激活的账号**连角色名都不该显示**
  （历史上曾出现"待审批账号显示为超级管理员"的自相矛盾画面）。
* "队员" = `users.status == 'active'`，此时才展开角色对应的权限点。

设计约束：权限判定**不写死角色名**，而是判定"权限点"（如 `log.edit.own`、`log.approve`），
角色只是权限点的预设集合 —— 这样二期加自定义角色时不用改代码。

## 4. 领域模型草案 ✅（结构已定，字段待补充）

### 4.1 Member 成员
- 呼号 Callsign（唯一）、编号（可选）
- **军衔 Rank**（身份/权限侧）：❓ 具体衔级表见 Q1-b
- **资质等级 Qualification Level**（能力认证侧）：学员 / 僚机 / 长机 / 教官
  - ⚠️ 军衔与资质是**两个完全独立的字段**，互不推导：一个人可以是"高军衔 + 低机型资质"（如转机型重新认证）
- 状态：现役 / 休整 / 退役 / 预备（注册待审批时为 `pending`，不可见内部内容）
- 角色（见 §3）、加入日期、简介、头像
- 资质明细（手工录入）：机型、等级、授予日期、授予人
- 变动历史：晋升、奖惩、状态变更（只追加，不修改历史）
- 🔒 真实姓名 / 联系方式 —— `command` 层，是否收集待定（Q7）

### 4.2 Campaign 战役
- 名称、时间范围、所属战区/剧本、状态（筹备/进行/结束）、公开简介与封面
- 关联：多个 Mission
- 汇总统计：总架次、总时长、交换比

> ⚠️ **「总时长」的口径：任务维度只算一次。**
> 多人飞同一任务时，各人的架次区间相互重叠；若按人次相加，
> 一个 4 人同飞 1 小时 13 分的任务会显示成 4 小时 24 分。
> 任务维度一律取各架次在空区间的**并集**（见 §4.3）。
> 按人的口径（排行榜、个人记录）仍是人次相加，两者在页面上分别标注。

#### 4.2.1 战役管理（BMS 战役存档解析）—— ✅ 已实现

联队上传 Falcon BMS 的战役存档 `.cam`，网站解析出**战场本身**的态势。
与 §4.2 的手工建档战役是同一实体的两种数据来源：手工建档记"我们要打什么"，
`.cam` 解析记"战场上实际发生了什么"。

- **解析范围**：`.cmp`（战役元数据/队伍/事件/中队）、`.uni`（单位流：飞行、
  编队、中队、营/旅/师、特混舰队、目标点）、`.obd`（目标点增量：占有方、
  补给、燃油、子部件状态）、`.tea`（队伍经验/资源/兵力/关系）、`.obj`、
  `.evt`、`.pol`、`.pst`；以及 BMS 安装目录下的剧场数据表
  （`Falcon4_CT/UCD/VCD/WCD/RCD/FCD`、`CampObjData.xml`、`OCD_*.XML`、`strings.txt`）
- **上传**：网页上传 `.cam`，SHA256 去重；需要服务器可读 BMS 安装目录
  （`GFVFW_BMS_INSTALL_PATH`）。权限点 `campaign.upload`，**不给普通成员**——
  一份存档会改变全联队看到的战局
- **存储**：每份存档都保留元数据、队伍状态与事件（构成战役进程时间线）；
  目标点与单位的明细**只保留最新一份**，历史归属由"目标点易手记录"重建
  （否则 6944 目标点 × 165 存档 ≈ 110 万行，对小型 VPS 过重）
- **展示**：战役列表 / 战场总览（兵力对比、目标点类型分布、最近易手、情报事件）
  / 态势图（服务端 SVG：目标点、单位、SAM 威胁环、靶心）/ 空中态势
  （中队序列、机型与任务分布、逐架飞行）/ 地面与海军 / 目标点筛选 /
  战役进程（归属走势、谁在推进、易手明细、胜负态势）/ 存档列表
- **实现方式**：将 CamReader（C#）移植为 Python（`gfvfw/campaign/`），
  保持"Python 单体"；已与 CamReader 的 `campaign_state.json` 逐项对拍
  326/326 一致
- **坐标口径**：BMS 战役网格 `0–1023`，原点在西南角，x=东、y=北，每格 1 km；
  部分文件存的是**英尺**且 `X` 是北、`Y` 是东（与网格相反），换算集中在
  `gfvfw/campaign/coords.py`


### 4.3 Mission 任务（= 一次出击）
- 任务编号、任务名称、日期时间（UTC + 本地）、任务类型（训练/巡逻/对抗/护航/对地/其他）
- 起降基地、简报文本、战役归属
- **归并元数据**：ACMI 录制时间窗、出现的呼号集合、归并确认状态
- 汇总：参战人数、**日志时长**（只算一次）、**记录时长**、**飞行员累计**（人次）、战果/战损
- 公开开关（`public` 战报精选 vs `members` 完整日志）

> **三个时长口径**（多人同飞时必然不等，不是数据错误）：
>
> | 口径 | 算法 | 用途 |
> |---|---|---|
> | **日志时长** | 各架次**在空区间**的并集 —— 同一段时间只计一次 | "这个任务实际飞了多久" |
> | **记录时长** | ACMI **录制时间窗**宽度（含起飞前/降落后） | "这段录像有多长" |
> | **飞行员累计** | 各架次在空时长**相加**（人次） | "大家一共飞了多少" |
>
> 实测 4 人同飞：日志时长 `1小时7分`、记录时长 `1小时13分`、飞行员累计 `4小时24分`。
>
> ⚠️ **`任务时长` 这个词已废弃** —— 它原先其实标在录制窗上，
> 把"录像多长"与"飞了多久"混成了一个量。详见 §5.7 与 §4.4 的说明。
>
> 日志时长在**读取时**计算（`services/stats.py::mission_flight_seconds`），
> 不只依赖 `missions.duration_seconds` 冗余列 —— 后者只在归并时刷新。
> 架次未记录降落时用「起飞 + 在空时长」估区间终点，避免该架次整段丢失。

### 4.4 Sortie 个人架次
- 归属 Mission + 归属 Member（**通过呼号映射**）
- 机型、**起飞/降落时间（该飞行员**自己的**在空起止，不是文件录制窗）**、日志时长、起降次数、航程
- 武器投放明细、击落、被击落/战损
- 超限与事故标记（过载/超速/撞地/坠毁）
- 数据来源：`acmi` / `manual`
- **ACMI 原始飞行员名**（用于审计映射是否正确）

### 4.5 AC M I 导入实体
- `AcmiFile`：原文件存储、SHA256、上传人、上传时间、解析状态、录制时间窗、场景名
- `AcmiActor`：文件内的飞行员/单位条目，含原始名称
- `PilotMapping`：`AcmiActor 原始名` → `Member` 的映射（可复用的别名表）
- `ImportBatch`：一次归并建议（含 N 个文件 → 1 个 Mission），状态：待确认/已确认/已拒绝

### 4.6 其他实体
- `Qualification` 资质记录、`Award` 荣誉/勋章、`Event` 活动与报名、
  `Announcement` 公告、`ForumThread/Post` 论坛帖、`Document` 资料文件、
  `AuditLog` 操作审计、`Rank` 军衔定义、`Application` 招新申请

### 4.7 入队流水线 ✅（已实现：注册 → 申请 → 管理员提升为队员）

> 用户同时选择了"自助注册+审批"与"招新申请表单"。为避免两套流程割裂，
> **合并为一条流水线**，招新只是这条流水线的对外入口。
>
> 🔴 **本轮修正（已实现）**：原设计是"申请 → 初审 → 发邀请码 → 申请人注册 → 激活"，
> 共五步、两个环节要人工。联队的口径最终收敛为
> **"游客注册后可查看所有公开的战役管理、飞行纪录、资料、统计数据；
> 注册之后再提交申请成为队员。"**
> 于是拆成**两步**：**先注册（立刻成为游客）→ 再申请（管理员提升为队员）**。

#### 三档身份（核心约定）

| 档位 | 判定 | 能看到什么 |
|---|---|---|
| **未登录访客** | 无会话 | 首页概览、注册页、登录页 |
| **游客** | 已登录，`users.status = 'pending'` | 上面全部 + **各区块的列表与汇总**（名册的呼号/军衔/飞行时长、飞行记录、战役管理列表、统计与排行榜、资料目录）+ 自己的申请进度 + 账号与密码设置 |
| **队员** | 已登录，`users.status = 'active'` | 上面全部 + **详情页与写操作**：任务详情与架次、战役态势（基地/兵力/地图）、ACMI 工作台、资料文件下载、Logbook 上传 |

> ⚠️ 边界是**列表 vs 详情**，不是"公开 vs 全锁"。改动时最容易漏的是
> **列表页里内嵌的写操作 UI**（ACMI 工作台），见 §2 的警告。

**落地方式**（`gfvfw/web/deps.py`）：

* 权限点判定不变（只判权限点，不判角色名）；**游客的权限点集合恒为空**
  —— 因为 `load_principal` 是**白名单**：只有 `active` 才展开角色权限。
* 于是"提升为队员"= 把 `status` 从 `pending` 改成 `active`，
  **不是加一个标记位**，而是真的把详情页与写操作开放给他。
* 两个守卫分工明确：
  * `require_login` —— **只要已登录**（游客也算）。用于**列表/汇总页**、
    账号页、申请页、申请进度页。
  * `require_member` —— **必须是队员**。用于一切**详情页**。
  * `require(权限点)` —— 隐含队员身份，用于一切写操作。

> ⚠️ **游客访问详情页必须给 403 说明页，不能重定向到登录页。**
> 游客已经登录了，重定向会造成「点详情 → 回登录页 → 登录页说已登录 →
> 再点 → 再回」的死循环，用户完全看不出自己差的是"被提升"这一步。
> 对应异常 `MemberRequired`（与 `LoginRequired` 分开）；
> 说明页里必须**列出游客现在能看什么**，否则他会以为整个系统都是锁的。

#### 流程（已实现）

```
① 公开注册  POST /register（用户名 / 密码 / 邮箱）
      │  同一个事务里：
      │    · 建 User(status='pending', registration_ip_hash=IP哈希)  ← 这就是「游客」
      │    · **不建 Application** —— 注册 ≠ 申请
      │    · **不建 Member**（名册只收队员）
      ▼
   立刻自动登录（游客零权限，少输一次密码）→ 各区块的**列表**随即开放
      │
      ▼
② 入队申请  POST /apply（**需登录**：呼号意向、飞行经历、意向、联系方式）
      │  · 落 Application(status='submitted')，也存 IP 哈希（R7）
      │  · 已有未撤销申请的人**不能重复提交**（避免刷一屏）
      ▼
   游客在 /apply/status 看进度
      │
      ▼
③ 管理员在 /applications 看到待审批列表（导航带角标）
      │  点「提升为队员」（呼号可改）
      ▼
· 建 Member(callsign=呼号)
· 分配 member 角色
· users.member_id 指向它、users.status = 'active'
· Application.status = 'activated'（**没有申请表的账号也能直接提升**）
· 写审计 application.promote（含改前/改后）
      ▼
该账号**立刻**能进详情页（无需重新登录）
```

拒绝则走 `POST /applications/{id}/reject`：账号转为 `suspended`（**不允许登录**），
申请标为 `rejected` 并记录原因。**刻意不删账号** —— 删了就没有"这个人申请过"的痕迹。

设计要点：

- 呼号**唯一性在申请阶段就校验**（防止重名抢占），提升时会**再校验一次**
  （名册重名会让 ACMI 归并认错人）——冲突时明确报错，不写入半个成员。
- 拒绝的申请保留记录（防止重复骚扰），但不进名册。
- **提升不会自动填军衔**：让该成员上传自己的 Logbook 即可自动获得（见 §5.6）。
- **激活后仍需上传一次 Logbook 与 Tacview**，才能建立"名册成员 ↔ 游戏内身份"的绑定。
- **注册不等于授权**：注册只证明"有个能登录的账号"。真正的授权动作只有
  "提升为队员"这一个。已登录的人再访问 `/register` 会被送回 `/apply`，
  免得一个人攒出两个账号。

#### 与"申请表 + 邀请码"原设计的差异（有意为之）

| 原设计 | 现在 | 为什么 |
|---|---|---|
| 5 步、人工初审 + 发邀请码 | 3 步（注册 → 申请 → 提升） | 邀请码只为一件事服务：确认邮箱可达。联队靠管理员人工联系，不需要多一层 |
| 申请即建账号（v2.0 的过渡形态） | **注册与申请分开** | 联队的口径是"注册之后**再**提交申请"。分开还有一个实际好处：游客一注册就能看列表，**不必先写一份申请**才知道系统长什么样 |
| `pending` 与账号同时产生 | 注册即 `pending`（游客） | 游客必须能登录才能"查看公开部分"，否则"游客"没有载体 |
| `invited` / 邀请码字段 | 保留在表里但**不再使用** | `Application` 模型不改结构，将来若需要邮箱验证可直接启用 |
| 申请时填用户名/密码 | 注册时填；申请只填呼号意向与经历 | 一个表单只做一件事：`/register` 管账号，`/apply` 管入队 |

## 5. ACMI 处理流程 ✅（核心流程）

```
上传 ACMI（成员自己 / 管理员批量）
      │
      ├─ 校验：格式、大小、SHA256 去重（防止重复上传同一文件）
      ├─ 存储原件（不入库，落文件系统 + 路径索引）
      ▼
解析（后台任务，进度可见）
      ├─ 读头部：录制起止时间、场景名、Tacview 版本
      ├─ 提取 Actor 列表（呼号 / PilotName / 机型 / 阵营）
      ├─ 提取事件流：武器投放、击毁、坠毁、超限
      └─ 累计航程（由位置变化计算，**仅出数值，不保留轨迹点** —— 见 §1.2）
      ▼
归并建议引擎
      ├─ 规则：录制时间窗重叠 + 呼号集合重合度 + 阵营一致
      └─ 输出：建议分组（可能 1 文件 = 1 任务，也可能 8 文件 = 1 任务）
      ▼
【人工确认页】★ 关键交互
      ├─ 每份文件选择：并入哪个 Mission / 新建 Mission / 忽略
      ├─ 合并、拆分、改归属；冲突与重合度可视化提示
      ▼
呼号映射
      ├─ 自动套用已有别名表
      ├─ 未识别的原始名 → 列出"未认领飞行员"，指派给 Member 或标记为"外部/敌方"
      ▼
生成 Sortie 记录 → 写入统计 → 归档原件
```

### 5.0 入口形态：ACMI 工作台 ✅（已实现，联队定稿）

**不设独立的 ACMI 上传页面。** 上面那条流程以「ACMI 工作台」的形式，
作为一个可折叠区块内嵌在三个业务页面里，并继承宿主页面的上下文：

| 宿主页面 | 战役 | 任务类型 | 归并结果 |

## 5.2 ACMI 格式实地勘察结论 ✅（2026 实测，非推测）

> ⚠️ **范围说明**：本节及以下技术结论来自对现有 193 份历史 ACMI 的**只读分析**。
> 这些历史文件**不导入、不统计**（见 §5.3）。分析目的仅为**摸清格式与判定阈值**，
> 使线上处理新上传文件时一次正确。

对 `G:\BMS\Falcon BMS 4.38\User\Acmi\` 实际取样分析结果。

### 容器格式：**ZIP 包着一个文本文件**
```
2026-08-04_10-27-51.zip.acmi        ← 扩展名像 acmi，实际是 ZIP
  └─ acmi.txt  (50,847 bytes)       ← 唯一成员，纯文本
```
- ⚠️ **解析器必须"先当 ZIP 尝试解压，失败再当裸文本读"**，两种形态都存在

### 文本格式：Tacview ACMI 2.1 —— **可读、易解析** ✅
```
FileType=text/acmi/tacview
FileVersion=2.1
0,DataRecorder=Falcon BMS 4.38.1
0,DataSource=Falcon 4.0
0,ReferenceTime=2024-8-16T00:00:00Z
9,T=26.409252|40.544404|579.12|0|3.9|124.6|631334.5|795291.49|117.6,
   AOA=3.9,CAS=174,CallSign=Tiger41,Coalition=Hellas,Color=Blue,
   Health=1,IAS=174,Mach=0.53,Name=F-16C B52M HAF,Pilot=Oblivion,Type=Air+FixedWing
#24488.051
9,T=26.409512|40.544285|579.21||4.2||631356.72|795278.59|,FuelWeight=5195,LockedTarget=0
```

| 发现 | 含义 |
|---|---|
| **`Pilot=Oblivion` 直接写在对象属性里** | ✅ **R3 风险大幅降低** —— ACMI 自带飞行员名，不必靠猜 |
| `CallSign=Tiger41` 是独立字段 | 战术呼号 ≠ 飞行员名，两者要分别处理 |
| `Name=F-16C B52M HAF` | 机型可解析，但含涂装/型号后缀，需归一化 |
| `#24488.051` 为时间戳行 | 其余行是**增量差分**（只写变化字段）→ 解析器需维护**对象状态机**，不是逐行独立记录 |
| 对象编号混用十进制与十六进制（`9`、`a`） | ⚠️ 解析陷阱：对象 ID 要按 **16 进制**解析 |
| `Health` / `Mach` / `FuelWeight` / `LockedTarget` | 战损、超限、交战的原始依据齐全 |

### 真实数据量级（决定性能设计）
```
文件数：197 个        总大小：1301 MB
最大单文件：约 21 MB   最小单文件：6.6 KB
```
- ⚠️ **R1 已消除**（用户决定不做回放）：单文件 21 MB、帧率极高（50 KB 文本含 2 万多个时间戳），
  这仍然意味着**解析器必须高效**（流式逐行处理，不可整文件载入内存后逐条正则匹配），
  但**不再需要任何为"播放"服务的降采样或切片设计**。
- ⚠️ 上传环节必须支持 **20 MB 以上文件**，需设置上传体积上限与超时策略。

### 时间来源 ✅（含一处已修的严重解析错误）

实测 ACMI 文件名时间为 UTC（`10-27-51`），而 BMS 自身日志为东八区（同一时刻记录为 `18:20:10`）。
若此规律成立，则**文件名可直接作为任务时间来源**；
而 `ReferenceTime` 是剧本地图纪元时间（`2024-8-16`），**绝不能当作真实日期使用**。

**三个时间量的正确关系**（`⚠️` 标注的是曾经的错误实现）：

```
                    文件名时间（= 录制终点，实测验证过：与末标记推导出的终点一字不差）
                         ▲
                         │
   t=0 基准点 ───────────┼───────── 录制起点 ───────── 录制终点
   （剧本纪元）           │          基准+首标记        基准+末标记
                         │
   首标记 常是个大数 ─────┘   末标记
   （实测 36000.2 = 10 小时）
```

| 量 | 定义 | 曾经错写成 |
|---|---|---|
| `min_relative_seconds` | 文件内**最小**时间标记 | **根本没记录** |
| `max_relative_seconds` | 文件内**最大**时间标记 | 正确 |
| **`duration_seconds`** | `max − min` | ⚠️ 取了 `max` 本身 |
| `recorded_start_at` | t=0 基准 + **首**标记 | ⚠️ 写成 t=0 基准点本身 |
| `recorded_end_at` | t=0 基准 + 末标记 | 正确 |

**为什么错得这么离谱**：BMS 的 ACMI 时间戳以**剧本纪元**（`ReferenceTime`）为基点，
不是以录制起点为基点，所以首个标记往往是个大数。用「末标记」当时长，
等于把整段战役已经过去的时间都算进这一次录制里。

**实测影响**（真实文件，非构造样本）：

| 文件 | 真实录制时长 | 旧算法报出 | 多报 |
|---|---|---|---|
| `2026-01-02_15-26-30.zip.acmi` | 4.5 秒 | 36004.7 秒 | 36000 秒（≈10 小时） |
| `2026-01-11_17-51-53.zip.acmi` | 2.8 秒 | 10802.9 秒 | 10800 秒（≈3 小时） |
| **联队实际上传的 `2026-08-08_14-16-23.zip.acmi`** | **1 小时 13 分** | **51 小时 31 分** | 50 小时 |

波及面（都已修正）：
* 归并页的「时长」列；
* 任务列表的「总时长」列与任务详情的「历时」；
* 「录制时间窗」的**宽度**（起点曾被推到剧本纪元，窗口比真实录制宽出整个首标记）；
* 解析器的「时长超阈值」告警 —— 会被这个错误**误触发**，任何首标记不为 0 的
  文件都会莫名其妙报超时。

**未受影响**：架次级飞行时长按采样间隔累加（`flight += delta_t`），
本就是时间段之和，因此一直是正确的；`/log/campaign`、`/log/training` 用的是
架次之和，也没受污染。

合成用例加上「标记不从 0 开始」的变体（`tests/acmi_parser_selfcheck.py` 的
`[1b]` 段），以及摄入链路的**不变量断言**「时间窗宽度 == 录制时长」

**老数据修正**：`scripts/reparse_acmi.py` 重解析原始文件并回填
（默认只预览，`--apply` 才写库）。由于 `min_relative_seconds` 无法从库里反推，
必须重解析 —— 原始 ACMI 都留在 `var/storage`，所以可重算。

## 5.4 人工修正与删除口径 ✅（上线后运维必需，已实现）

上线后数据一定会录错（文件传错、归并归错、时长明显不对）。**必须有界面能改能删**，
否则使用者会绕过应用直接改数据库 —— 那就同时失去审计与软删除两道防线。

### 可修正的项与入口

| 对象 | 操作 | 路径 | 权限点 |
|---|---|---|---|
| 任务 | 改名称/类型/可见性/时间窗/起降基地/简报 | `GET,POST /missions/{id}/edit` | `log.edit.any` |
| 任务 | 删（= 撤销归并） | `GET,POST /missions/{id}/delete` | `log.delete` |
| 架次 | 改时长/航程/机型/归属人/起降/起降次数/备注 | `GET,POST /sorties/{id}/edit` | 本人 `log.edit.own`；他人 `log.edit.any` |
| 架次 | 删 | `POST /sorties/{id}/delete` | `log.delete` |
| 架次 | 补录（ACMI 丢失/未录） | `GET,POST /missions/{id}/sorties/new` | `log.approve` |
| ACMI 文件 | 删（**仅未归并的**） | `POST /acmi/{file_id}/delete` | 本人 `acmi.upload`；他人 `acmi.upload.any` |
| 战役存档 | 删 | `POST /theater/{campaign_id}/saves/{save_id}/delete` | `campaign.manage` |
| 战役 | 作废 / 恢复 | `POST /campaigns/{id}/delete` / `POST /campaigns/{id}/restore` | `campaign.manage` |
| 名册成员 | 作废 / 恢复 | `POST /members/{id}/delete` / `POST /members/{id}/restore` | `member.void`（仅超管） |
| 名册成员 | 账号与成员**解绑** | `POST /members/{id}/unbind` | `member.delete` |

> **入口必须可见**：删除名册成员与作废战役的 handler 都早就写好了，但前者
> **没有任何模板引用**、后者只藏在编辑页最下面 —— 功能"存在"却点不到，等于没做。
> 所以两者的入口都在**详情页底部的「危险操作」面板**里，且
> `scripts/live_edit_check.py` §8b 专门盯着入口是否真的渲染出来。
> 恢复入口在各列表页的 `?deleted=1`（「显示已作废」）。

### 账号、成员与访问权（v2.7 补充）

名册成员（``members``）与登录账号（``users``）是两张表，靠 ``users.member_id``
一对一绑定。**权限来自"成员身上的角色"**，所以这三个动作在访问权上的效果必须分开说：

| 动作 | 账号 | 名册成员 | 角色 | 结果 |
|---|---|---|---|---|
| 解绑 | 降为 `pending`（游客），`member_id=None` | 保留 | **不动** | 能登录、能看列表汇总、**零权限** |
| 作废成员 | 一并停用（`suspended`），不能登录 | 标 `deleted_at` | 保留在库里 | 人从名册消失，历史数据全保留 |
| 恢复成员 | 若被停用则恢复为 `active` | 清 `deleted_at` | 本来就是 | 回到原状 |

**解绑为什么不动角色**：角色挂在 `member_id` 上，是这个人的**队内身份**，
不是某个登录账号的属性。所以"绑错账号 → 解绑 → 重绑正确的账号"之后，
指挥官权限会正确地跟着成员回来；反之若解绑就清角色，一次误操作就得重授一遍权。

**解绑为什么必须降为游客**：`Principal.is_member` 只看 `users.status`，
不看有没有成员行 —— 留着 `active` 的话它在 `require_member` 眼里**仍然是队员**，
能进所有详情页，只是恰好没权限点，是个自相矛盾的半成品状态。

**两条防自锁的闸**（不是权限判定，是防不可逆的运维事故）：

1. 不能用当前登录的账号给自己解绑；不能作废自己所在的成员记录；
2. 不能作废／解绑**最后一个能登录的 owner**（条件是"有未撤销的 owner 角色"
   **且**"绑着 `active` 账号"）。否则界面上再没有人能授权，只能上服务器
   用 `gfvfw.cli grant-role` 救。

### 三条硬性口径

**（1）已归并的 ACMI 不得直接删除。**

请求返回 400，文案指向任务详情页：

> 该文件已归并到任务「X」，不能直接删除。请先到任务详情页删除该任务 ——
> 删除任务会把文件退回待归并，之后既可删除也可重新归并。

理由：`acmi_files` 是硬删除（该表没有 `deleted_at`），若允许删已归并的文件，
就等于**绕过软删除**在飞行日志上挖洞：任务还在、架次还在，但原始记录没了，
审计再也无法回溯"这个时长是怎么来的"。

**（2）「任务时长」不随编辑任务时间窗而变化。**

任务时长是各架次在空区间的**并集**（§4.3），时间窗只是元数据（展示与筛选）。
编辑页必须**明说**这一点，否则用户改完时间以为时长会变，会误判功能失效。
编辑页同时显示当前任务时长与架次数量作为参照。

**（3）删除一律软删除，唯一例外是 `acmi_files`。**

| 表 | 删除方式 | 原因 |
|---|---|---|
| `members` / `campaigns` / `missions` / `sorties` | **软删除**（置 `deleted_at`） | 需求 R11：历史日志不得出现空洞；误删可恢复 |
| `acmi_files` | **硬删除**（行 + 磁盘原件） | 该表无 `deleted_at`；且**同一文件必须能重新上传**，否则唯一索引会拒绝重传 |

删任务时：任务与其下架次置 `deleted_at`，同时把 `acmi_files.mission_id` /
`batch_id` **置空退回待归并** —— 这就是"撤销归并"。它可以一次解决三种诉求：
删错了的归并、改归属重做归并、单纯想重传文件。

删战役存档时：级联删除该存档的子表行（队伍状态/目标点/易手/单位/事件），
并清理磁盘上的 `.cam`；若删的是**最新**存档，页面会提示"战局已回退到上一存档"。

**作废战役**时：`campaigns.deleted_at` 置位，并把其下任务的 `campaign_id`
**置空退回未归属**（任务与架次一条都不删）。**恢复时不会自动归回** ——
作废这个动作没有记录那些任务原本属于谁，事后分不清哪些本来就未归属，
所以恢复只是"把战役放回列表"，要归回请用详情页的「归入任务」。
宁可让用户多点一次，也不凭猜测挪数据。

**作废成员**时：`members.deleted_at` 置位，**同时把绑定的登录账号停用**
（`users.status='suspended'`）。只标名册行不动账号的话，那个人照样能登录、
照样是队员 —— 那是"看起来生效了"的假删除。历史架次与 Logbook 归档按
`member_id` 关联，**全部保留**；恢复成员时把被停用的账号一并恢复为 `active`。

### 人工改动的留痕要求（防止污染统计）

人工填写的数字与 ACMI 解析结果**必须在数据层可区分**，否则统计失去可信度：

| 字段 | 人工改动后 |
|---|---|
| `sorties.data_confidence` | 降为 `estimated`（页面显示「手动/估算」徽标） |
| `sorties.data_source` | 补录的架次为 `'manual'` |
| `sorties.edited_by` | 记操作者 —— 指向 `users.id`（**不是** `members.id`：改的人可能已不是成员） |
| `sorties.edit_note` | 人工填写的修改原因 |
| `audit_log` | 谁 / 何时 / 改前 / 改后 |

单位换算与本地时间转换**只允许一处**：`web/forms.py`
（`parse_local_datetime` / `_secs_from_hhmm` / UTC+8⇄UTC）。模板与路由中
不得出现第二份换算逻辑。

### 权限边界（按权限点，不按角色名）

| 角色 | `log.edit.own` | `log.edit.any` | `log.approve` | `log.delete` |
|---|---|---|---|---|
| owner | ✓ | ✓ | ✓ | ✓ |
| commander 指挥 | ✓ | ✓ | ✓ | **✓** |
| instructor 教官 | ✓ | ✓ | ✓ | **✗** |
| member 成员 | ✓ | ✗ | ✗ | ✗ |

> 教官可改、可批，但**不可删** —— 这是刻意的差异，也只有"查权限点"能表达它。
> 所有边界在服务端强制（无权限者直接构造请求得 403），页面上只是隐藏按钮。

## 5.5 账号与密码 ✅（上线前必做，已实现）

密码用 **argon2id** 单向哈希存储（`security.py`），**不可逆、无法找回**。
所以必须同时提供两条路径 —— 只有其一都是残缺的：

| 路径 | 入口 | 适用 |
|---|---|---|
| 本人自助改密 | `GET,POST /account/password`（右上角名字 →「账号」） | 记得当前密码 |
| 运维重置 | `python -m gfvfw.cli set-password` | 忘记密码 / 账号被锁 |

### 硬性要求

**（1）改密必须验证原密码。**

仅凭登录态不够：浏览器被借用、Cookie 被窃时，只凭会话就能改密码，
等于把账号彻底交出去。这是「有登录态」与「能证明是本人」的区别。

**（2）CLI 重置必须同时解除登录锁定并清空失败计数。**

账号被锁（连续 5 次失败锁 15 分钟）**正是最需要重置密码的场景**。
若只更换哈希而保留 `locked_until`，运维会以为重置失败，然后去排查一个
根本不存在的问题。实测输出会明确写「已解锁：是（此前处于登录锁定）」。

**（3）强度策略 Web 与 CLI 共用同一个函数**（`security.password_problem`）。

否则会出现「网页不让设的密码命令行能设」—— 两套规则迟早不一致，
而**较松的那一方会变成实际生效的策略**。

策略选择（有意如此）：

| 项 | 值 | 理由 |
|---|---|---|
| 最短长度 | 8 位 | 内部系统，够用 |
| 复杂度 | **不强制**大小写/数字/符号 | 强制复杂度只会逼出 `Passw0rd!`、`Abc12345`，实际熵更低且更难记 |
| 弱口令 | 拦常见口令与联队相关词（`password`/`12345678`/`falconbms`…） | 拦"最容易被撞开的那批"，不追求完备 |
| 上限 | 200 位 | 防止有人用超大输入打服务（argon2 会把整串喂进去） |
| 首尾空格 | 拒绝 | 静默的空格是"密码明明对却登不上"的经典原因 |

真正的防线是 **argon2id + 登录锁定**，不是口令复杂度规则。

**（4）改密失败不计入登录失败次数。**

否则用户改密时打错两次原密码，就会被自己的账号锁在门外。
这与登录失败是**不同性质**的事件：前者是已登录用户在证明身份，
后者是匿名者在猜测凭据。

**（5）"改密使其他会话失效"做不到，且必须在页面上明说。**

会话 Cookie 里只存 `user_id`，没有可作废的版本号；要让其他设备掉线，
就得给 `users` 加 `session_version` 并每次请求比对。当前**未做**，
因此页面明确告知这一限制，并给出「怀疑被盗用时联系运维停用账号」的路径。
**与其假装安全，不如把边界写清楚。**

### 留痕

改密成功、改密失败、CLI 重置都写审计（谁 / 何时 / 对哪个账号 / 原因）。
审计里**不存密码本身**，只存时间戳与状态 —— 审计表是只增不改的，
写进去的东西会永久留存。

## 7. 技术选型（部署环境由本方案决定）

用户未指定部署环境，因此**选型约束是"开发机 Windows + 部署可迁移"**，不绑定单一平台。

### 7.1 架构

| 项 | 建议 | 理由 |
|---|---|---|
| 架构 | **单体 Web 应用**（服务端渲染或前后端分离皆可） | <100 人规模，微服务是自找麻烦 |
| 数据库 | SQLite（开启 WAL 模式） | 已确认基线 |
| 数据访问 | 经 **ORM/查询构造器** 抽象，禁用 SQLite 专有语法 | 未来可平滑迁 PostgreSQL，且迁移动因很可能是"分析查询变慢" |
| 文件存储 | 本地文件系统 + 数据库存路径与 SHA256 | ACMI 与手册文件不入库 |
| 后台任务 | **必需的简单任务队列**（进程内队列或独立 worker） | ACMI 解析是耗时操作，不能阻塞 Web 请求 |
| 时区 | **数据库统一存 UTC**，展示按配置时区转换 | 虚拟联队常有跨时区成员，事后补录时区混乱会污染统计 |

### 7.2 语言/框架的取舍（待定 Q4-b）

| 方案 | 优势 | 劣势 | 适配度 |
|---|---|---|---|
| **Python**（FastAPI/Django） | ACMI 解析、数据分析生态最强；后续做轨迹处理/统计最省力 | 部署需装运行时（可用容器缓解） | ⭐ **已选定** |
| **Node.js**（NestJS/Next.js） | 前后端同一语言；部署轻 | 二进制文件解析与科学计算生态弱一些 | 未采用 |
| **Go** | 单二进制部署最省心，性能好 | 解析 ACMI、做数据分析的库少，开发速度慢 | 未采用 |

> ✅ **决策（v0.6）**：**Python + 单体应用 + SQLite + 简单任务队列**。
> 理由：用户授权按"最好维护"选择；本项目技术核心是**文件解析与统计分析**，
> Python 在此方向的库最成熟、容错处理成本最低。
> 维护性优势：单进程、单数据库、依赖少、可整体备份，一人可长期维护。
>
> 💡 具体框架倾向 **FastAPI（后端）+ 服务端渲染模板**：
> 一期不做前后端分离，避免同时维护两套代码与两套构建流程 —— 这是"最好维护"的关键取舍。

```
Internet
   │  HTTPS (443)
   ▼
[Caddy 反向代理]  ← 自动申请/续期证书，托管静态文件
```

### 8.1.1 补充实测（**结论已被推翻**：格式解出，自动解析已实现）

> 🔴 **本节保留原文以便追溯判断过程，但结论已作废。**
> §8.1 与 §8.1.1 的最终结论是"归档 + 手填 + 确认"；**该结论是错的**，
> 且 §5.6 的旧实现（手填表单）已随之删除。新的结论见本节末尾「结论修正」。

§8.1 当初的判断依据只是"看起来是二进制、没有公开文档"。本轮做了可复现的实测，
把"看起来像"换成事实（脚本：`scripts/lbk_probe.py`、`lbk_keyrecover.py`、`pe_strings.py`）：

| 实测项 | 结果 | 说明 |
|---|---|---|
| 四个真实样本大小 | **全部 372 字节** | 定长结构（不是压缩产物） |
| 重复结构 | 每样本自 `0x00E8` 起有**周期 42** 的重复块 | 尾部疑似固定填充 |
| 样本间关系 | `Obsequies` 与 `SZSZS` 在偏移 189 起 **177 字节完全相同** | 该区间内容与飞行员身份无关 |
| 异或分析 | 首 16 字节在 `Oblivion`/`Obsequies` 间**恰好差 0x20**（ASCII 大小写位） | 说明头部有定长字段，但并非明文 |
| 常量密钥假设 | **被否决** —— "明文含呼号 + 固定 XOR 密钥"在所有偏移上都找不到共同隐式密钥 | 见 `lbk_keyrecover.py` |
| 官方读取器 | `LogbookEditor.exe` 142 KB，**32 位 MinGW/Qt4**（依赖 QtCore4/QtGui4/mingwm10） | 无法在服务器上自动化调用 |
| **加密 API 导入** | **一个都没有**（仅 KERNEL32 / msvcrt / Qt4 / MinGW 运行时） | 所以混淆是**内联自实现**，不是调用系统密码学库 |

**当时的结论（现已作废）：**

1. 格式是私有且自实现混淆的，逆向需要反汇编 91 KB 的 32 位 x86（本机 REA 的
   Ghidra/Hopper 提供方均不可用：Ghidra 未安装且**拒绝 32 位 PE**，Hopper 仅 macOS）；
2. 更关键 —— **即便逆向成功，BMS 版本升级可能改动格式并静默读出错数据**，
   而错数据会直接污染名册里的军衔与累计时长；
3. 一期只有 4 个样本、且都是**近乎空的存档**，没有足够的对照数据验证解析正确性。

> ~~**因此正式方案定为：归档原件 + 成员手填声明值 + 指挥确认。**~~

#### 结论修正（本轮）：格式**已解出**，自动解析已实现

上面三条"证据"**都没有错**，但**推不出"不可解"**：

| 当时的观察 | 为什么不足以推出不可解 |
|---|---|
| 大小恒为 372、周期 42、两两异或找不到密钥流 | 这些都是**否定性**统计 —— 只能说明"不是简单 XOR 流密码/压缩包"。真实模型是**逐字节链式差分**：`P[i] = C[i] ^ key[i%21] ^ C[i-1]`，每个字节都依赖前一字节，用"两两异或消掉密钥流"的思路自然什么都得不到 |
| 官方读取器无加密 API 导入 | 恰恰相反：这正说明密钥是**内联常量**。密钥就在 `.data:0x418000`，是一句 21 字节的 C 字符串 `"Falcon is your Master"` |
| Ghidra/Hopper 不可用 | 反汇编 32 位 PE 用 `objdump`（MinGW 自带）就够了。真正需要的是**跟着 IAT 调用点**找到 `fread` 旁边的解码函数 |
| 样本太少、都是空存档 | 实为 15 个文件 / 7 个唯一内容；其中同一人的 **4 份带日期快照**（02-27 / 03-03 / 03-11 / 09-22）提供了时间序列，足以验证字段语义 |
| BMS 升级可能静默改格式 | **这条依然成立**，但正确应对不是"不解析"，而是**把解析失败当正常分支**：原件照样归档、页面如实显示「已归档、未解析」、解析器改进后「重新解析」回填 |

**解出的格式**（全部为实测，非推测；细节见 §5.6 与 `gfvfw/lbk_parser.py`）：

* 长度**必须恰好 372 字节**（官方读取器 `fseek/ftell` 后强校验）；
* 变换是差分异或链，密钥 `"Falcon is your Master"`，链初值 `0x58`，
  末尾 `uint32` 哨兵必须为 0；
* 编码与解码是官方工具里**两个不同的函数**（`0x40300c` / `0x40305c`），
  都以密文前一字节作链值 —— **不是自身的逆**；
* 已确证字段：姓名 / 呼号 / 中队 / 日期 / `f32` 累计飞行小时 /
  `f32` ace factor / `u32` 军衔下标 / 6 个勋章字节；
* 统计区 `0x54..0x88`（25 个计数器）**已按联队对照表（`log.xlsx`）确认含义**
  并正式命名（战役胜负 / 执行任务数 / 击杀 / 狗斗 / 得分等，
  见 `gfvfw/lbk_parser.py`）—— 只展示，其中 `0x6a` 执行任务数写入名册「累计架次」；
* `0x98..0x168` 的只读 u32 **含义未确认**，只展示、不入库。

## 5.6 BMS Logbook 上传与自动解析 ✅（已实现）

> 见 §8.1.1 的结论修正），2026-09 修正为 `0x6a`。修正后需用
> `scripts/reparse_logbooks.py --apply` 或页面「重新解析」回填，
> 否则名册里留的是击落数（偏小）。日后改动架次偏移必须先补上同类证据。

**（2）解析失败必须保住归档，且不得谎报。**

BMS 版本升级可能静默改动格式。因此"解析失败"是**正常分支**而不是异常：

| 情况 | 行为 |
|---|---|
| 解析失败 | 原件**照常归档**；`parse_error` 记下原因；页面显示「解析失败」面板；`did=uploaded_unparsed` |
| 名册 | **不动**（保住上一次成功解析的值） |
| 展示 | 解析结果取**最新一份解析成功的**归档，不被失败信息顶掉 |
| 补救 | 解析器改进后用 `POST /logbook/{id}/reparse` 在原件上重跑，不必让成员重传 |

**（3）没有手填路径，也没有审核。**

联队要求"Logbook 里的数据直接归档"。因此：

* 页面上**没有任何手填数值的输入框**；
* 早先的 `declare()` / `apply_to_roster()` / `/declare` / `/reapply`
  **已整体删除** —— 它们是绕过解析的第二条写入通路，
  会让"名册里的值到底来自文件还是人手"无法回答；
* 现在写入名册的唯一入口是 `services/logbook.py::apply_parsed`。

可追溯性由三件事保证，取代了审核环节：

| 手段 | 作用 |
|---|---|
| `members.rank_source = 'logbook'` | 明确这是游戏来源，不是人工裁决 |
| `rank_updated_by` / `logbook_updated_by` / `confirmed_by` | 谁写的、什么时候写的 |
| `audit_log` 的 `logbook.upload` / `logbook.reparse`（含改前/改后） | 完整变更历史，可回退 |

> ⚠️ **安全含义（已知并接受）**：`logbook.upload` 给到了普通成员，
> 所以成员可以为**自己**上报军衔与累计飞行量。这在权限矩阵里原本属于
> `member.rank.edit`（"军衔/资质属敏感变更"）。区别在于现在是
> **上传游戏生成的文件**而非自填数字，且文件按 SHA256 留证、页面把原始值与来源
> 都摊开。联队选择"信任游戏内数据 + 留痕可追溯"而不是"事前审批"。

**（4）Logbook 不参与资质。**

`.lbk` 里没有资质字段。名册里的资质**只由教官手工授予**。
早先"成员自报资质并同步 `source='logbook'` 的那一批"随手填路径一起移除 ——
也因此不再存在"一次 Logbook 登记撤销教官考核记录"的风险。

**（5）三个"时长"必须分别标注。**

| 量 | 来源 | 实测同一任务 |
|---|---|---|
| **Logbook 累计时长**（`members.logbook_hours_seconds`） | BMS Logbook 的**跨存档历史总量** | 含本站上线前的飞行（实测 296 小时 17 分） |
| **日志时长** | 各架次**在空区间**的并集，多人同飞只算一次 | 4032 s = **1 小时 7 分** |
| **记录时长** | ACMI **录制时间窗**宽度（起飞前 + 在空 + 降落后） | 4418 s = **1 小时 13 分** |

三者**对不上是正常的**，页面上分别标注并明确写"不要互相校验"。

**（6）归档是硬删除。**

`logbook_files` 无 `deleted_at`（与 `acmi_files` 同理）：
唯一约束 `(member_id, sha256)` 要成立，就必须"删干净才能重传同一个文件"。

### 历史归档回填

自动解析上线前归档的文件没有解析结果。用
`scripts/reparse_logbooks.py [--apply]` 从原件回填（幂等）。

## 5.7 日志时长 vs 记录时长 ✅（本轮澄清并修正）

**问题**：原先 `sorties.takeoff_at` / `landing_at` 直接写入文件的
**录制时间窗**，导致同一 ACMI 里**四个飞行员的起降时刻完全相同**，
"任务时长"因此退化成录制窗宽度（1 小时 13 分），而各人实际在空只有约 1 小时 6 分。
两个不同的量被混成了一个，且页面上只标注为"任务时长"。

**修正**：

1. **解析器**新增每个对象的**在空区间**（`airborne_start/end_relative_s`）：
   以速度证据（CAS/Mach）判定，起点取**上一个采样时刻**
   （因为该采样间隔被整段计入了飞行时长，否则区间会小于累计值，
   出现"多人同飞的日志时长比其中单人还短"的自相矛盾）。
2. **摄入**把在空区间换算成绝对时间写入 `sorties.takeoff_at` / `landing_at`
   —— 现在是**各人自己的**起降时刻；区间缺失时才退回录制窗。
3. **口径与命名**：

   | 名称 | 算法 | 出现在 |
   |---|---|---|
   | **日志时长** | 各架次在空区间的**并集**（只算一次） | 任务详情、任务列表、战役/训练记录、概览、成员档案 |
   | **记录时长** | `mission.ended_at − started_at`（录制窗） | 任务详情、ACMI 工作台 |
   | **飞行员累计** | 各架次在空时长**相加**（人次） | 任务详情、排行榜、个人记录 |

   三者满足不变式：`最长单人 ≤ 日志时长 ≤ 记录时长`、`日志时长 ≤ 飞行员累计`。
4. **历史数据回填**：`scripts/reparse_acmi.py --apply --all`
   （本次语义变更必须加 `--all`，因为老行的 `min_relative_seconds` 已不为 NULL）。
   该脚本同时补写摘要 JSON 里缺失的在空区间字段。

## 5.8 `/enroll`：一步开队员账号 ✅（已实现；**公开**，见 v2.6）

**联队要求**："直接注册为队员"。三档身份的正常路径依旧是
"注册（→ 游客）→ 提交申请 → 管理员提升为队员"，但联队需要一条
**不经申请**的旁路。

**形态（v2.6 变更后定稿）**：**对外公开**的固定路径页，**不进导航**。

| 维度 | 结论 |
|---|---|
| 入口 | 固定路径 `/enroll`，**不进导航**，只能靠链接进入 |
| 守卫 | **无 —— 不需要登录，也不需要任何权限**（联队口径，v2.6 起） |
| ⚠️ 链接算凭证吗 | **算。** 公开 ⇒ 拿到链接的人能给自己开一个立刻生效的队员账号（能看队内全部内容、能提交数据）。「不在导航」**不是**安全措施 —— 地址固定在源码里。**发给谁、发到哪个群要自己拿捏** |
| 收回公开 | `GFVFW_ENROLL_OPEN=false` + 重启 ⇒ 恢复为 `require(application.review)`（与审批页同一权限点）。**不改代码** |
| 批量刷号兜底 | 按来源 IP 每日额度 `GFVFW_MAX_ENROLL_PER_IP_PER_DAY`（默认 20）。它**不改变**"谁都能开号"这个权限模型，只挡"一个来源无限刷"。额度过半时会给出可读提示（429） |
| 模式 | ① **用名册里已有的呼号**（下拉只列**还没有账号**的队员）② **新建队员**（同时建 `Member(status='active')` + `User(status='active')` + `member` 角色） |
| 登录名可否等于呼号 | **可以**（联队口径，v2.6 起）—— 见下方"同名规则" |
| 为什么不给选角色 | 收敛权限面：这个页面的职责只是"开账号"，授权走 `/applications` 或 `grant-role` |
| 并发 | 模式① 在 **POST 时再查一次** `has_account`（TOCTOU），重复开号返回可读 400 |
| 不自动登录 | 开完号必须自己去 `/login`。刻意如此 —— 管理员常替别人开号，自动登录会把管理员自己的会话换成新账号的 |
| 留痕 | `audit_log(action='member.enroll')`，记呼号、登录名、所用模式、是否公开模式、`identical_name`；匿名开号时 `actor_user_id` 为空 |

**同名规则：两个命名空间允许同名（v2.6 变更）**

`members.callsign`（游戏身份、ACMI 归并键）与 `users.username`（登录名）
是两个独立命名空间。v2.3 曾**禁止**两者同名，理由是
`Principal.display_name` 对游客会回退到 `username`，于是"登录名等于某个呼号"
的账号在界面上看起来就是那位队员（冒充）。

**但联队的实际口径是"用呼号当登录名"，那条禁令把最自然的用法挡在门外。**
所以 v2.6 改为**消除"看起来像"本身**，而不是禁止重名：

1. 导航栏的名字旁边**始终**紧跟身份标签（`identity_label`：访客 / 游客 / 角色名），
   所以「Viper 游客」与「Viper 队员」不会混为一谈；
2. 入队审批页把该列明确标成**登录名**，并写明"登录名可能与呼号相同，
   看呼号那一列"；
3. **真正把关的是呼号唯一性**：提升为队员 / 新建成员 / CLI 都照旧用
   `callsign_owner` 拦重名，不会出现两个同名成员；
4. **同名换不来任何权限**：ACMI 认领需要 `ACMI_CLAIM_PILOT`（仅队员），
   与登录名无关；游客档位不受影响（队内详情页仍 403）。

即：**重名现在允许，但重名不换来任何权限。**
`gfvfw/services/naming.py` 仍是唯一裁判（大小写不敏感、排除软删除成员、
同时比对待审申请的意向呼号），只是不再做跨命名空间的互斥检查。

测试：`tests/access_selfcheck.py` §11（`/enroll` 对四种身份都 200、
页面写明"链接就是凭证"与收回开关、两种模式、重复开号 / 呼号重名 /
呼号被申请占用 / 弱密码 / 缺 CSRF、失败时**不得留下半个成员行**、
审计落库）、§12（同名**被允许**、同名游客**仍是游客**且进不了详情页、
呼号自身唯一性没放松、CLI 报错可读且允许同名）、
§13（两道闸门：IP 额度 429、`GFVFW_ENROLL_OPEN=false` 后匿名 303 /
游客与队员 403 / owner 200）。
