## 0. 一句话定位

一个面向 **Falcon BMS** 虚拟飞行联队的、**公开前台 + 分权限成员后台**的网站，

### 1.2 视频回放明确排除 ✅（本轮决定）

**不做网页轨迹回放。网站的职责边界是：接收 ACMI 文件 → 解析 → 记录结构化数据。**

| 项 | 决定 |
|---|---|
| 上传 ACMI 原件 | ✅ 做（归档保存，供下载） |
| 解析并记录数据 | ✅ 做（时长、名单、武器、战损、超限等） |
| 网页内地图/轨迹回放 | ❌ **不做** |
| 看回放的方式 | 成员下载 ACMI 原件，用**本地 Tacview** 打开 |

**这条决定消除的成本**（原计划中技术风险最高的部分）：

| 被消除的工作 | 原风险 |
|---|---|
| 服务端轨迹降采样管线（1~2 Hz） | R1 |
| 轨迹数据切片与分页传输接口 | R1 |
| 前端地图库集成与坐标系转换（经纬度 ↔ 战区坐标） | R1 |
| 浏览器端动画/时间轴渲染引擎 | R1 |
| 为 21 MB 单文件设计的分块流式加载 | R1 |

⚠️ **但上传体积约束依然存在**：ACMI 原件仍要上传与归档，
实测单文件最大 **21 MB**（197 文件 / 总计 1301 MB），
因此上传环节仍需支持大文件与合理超时策略 —— 只是**不再需要为"播放"做任何优化**。

## 2. 内容可见性三层模型 ✅

贯穿**所有实体**的一个字段（`visibility`），而非靠"页面藏起来"。

| 层级 | 谁能看 | 典型内容 |
|---|---|---|
| `public` 公开 | 任何人（含未登录、搜索引擎） | 战役概况、战报精选、荣誉榜、招新、成员呼号与飞行统计 |
| `members` 内部 | 已登录成员 | 完整飞行日志、ACMI 原件、任务日历、论坛 |
| `command` 指挥层 | 管理员/联队指挥 | 战损、失误、处罚记录、真实姓名、联系方式、账号信息 |

> ⚠️ 注意：`command` 层包含个人隐私数据（真实姓名、联系方式）。
> 需明确**是否收集**、**留存期限**、**成员能否要求删除**（见 §8 待定 Q7）。

| 角色 | 说明 | 关键权限 |
|---|---|---|
| `owner` 超级管理员 | 系统所有者 | 全部权限、角色授予、系统配置、备份 |

## 4. 领域模型草案 ✅（结构已定，字段待补充）

### 4.1 Member 成员
- 呼号 Callsign（唯一）、编号（可选）
- **军衔 Rank**（身份/权限侧）：❓ 具体衔级表见 Q1-b
- **资质等级 Qualification Level**（能力认证侧）：学员 / 僚机 / 长机 / 教官
  - ⚠️ 军衔与资质是**两个完全独立的字段**，互不推导：一个人可以是"高军衔 + 低机型资质"（如转机型重新认证）
- 状态：现役 / 休整 / 退役 / 预备（注册待审批时为 `pending`，不可见内部内容）
- 角色（见 §3）、加入日期、简介、头像
- 资质明细（手工录入）：机型、等级、授予日期、授予人
- 变动历史：晋升、奖惩、状态变更（只追加，不修改历史）
- 🔒 真实姓名 / 联系方式 —— `command` 层，是否收集待定（Q7）

### 4.2 Campaign 战役
- 名称、时间范围、所属战区/剧本、状态（筹备/进行/结束）、公开简介与封面
- 关联：多个 Mission
- 汇总统计：总架次、总时长、交换比

> ⚠️ **「总时长」的口径：任务维度只算一次。**
> 多人飞同一任务时，各人的架次区间相互重叠；若按人次相加，
> 一个 4 人同飞 1 小时 13 分的任务会显示成 4 小时 24 分。
> 任务维度一律取各架次在空区间的**并集**（见 §4.3）。
> 按人的口径（排行榜、个人记录）仍是人次相加，两者在页面上分别标注。

#### 4.2.1 战役管理（BMS 战役存档解析）—— ✅ 已实现

联队上传 Falcon BMS 的战役存档 `.cam`，网站解析出**战场本身**的态势。
与 §4.2 的手工建档战役是同一实体的两种数据来源：手工建档记"我们要打什么"，
`.cam` 解析记"战场上实际发生了什么"。

- **解析范围**：`.cmp`（战役元数据/队伍/事件/中队）、`.uni`（单位流：飞行、
  编队、中队、营/旅/师、特混舰队、目标点）、`.obd`（目标点增量：占有方、
  补给、燃油、子部件状态）、`.tea`（队伍经验/资源/兵力/关系）、`.obj`、
  `.evt`、`.pol`、`.pst`；以及 BMS 安装目录下的剧场数据表
  （`Falcon4_CT/UCD/VCD/WCD/RCD/FCD`、`CampObjData.xml`、`OCD_*.XML`、`strings.txt`）
- **上传**：网页上传 `.cam`，SHA256 去重；需要服务器可读 BMS 安装目录
  （`GFVFW_BMS_INSTALL_PATH`）。权限点 `campaign.upload`，**不给普通成员**——
  一份存档会改变全联队看到的战局
- **存储**：每份存档都保留元数据、队伍状态与事件（构成战役进程时间线）；
  目标点与单位的明细**只保留最新一份**，历史归属由"目标点易手记录"重建
  （否则 6944 目标点 × 165 存档 ≈ 110 万行，对小型 VPS 过重）
- **展示**：战役列表 / 战场总览（兵力对比、目标点类型分布、最近易手、情报事件）
  / 态势图（服务端 SVG：目标点、单位、SAM 威胁环、靶心）/ 空中态势
  （中队序列、机型与任务分布、逐架飞行）/ 地面与海军 / 目标点筛选 /
  战役进程（归属走势、谁在推进、易手明细、胜负态势）/ 存档列表
- **实现方式**：将 CamReader（C#）移植为 Python（`gfvfw/campaign/`），
  保持"Python 单体"；已与 CamReader 的 `campaign_state.json` 逐项对拍
  326/326 一致
- **坐标口径**：BMS 战役网格 `0–1023`，原点在西南角，x=东、y=北，每格 1 km；
  部分文件存的是**英尺**且 `X` 是北、`Y` 是东（与网格相反），换算集中在
  `gfvfw/campaign/coords.py`


### 4.3 Mission 任务（= 一次出击）
- 任务编号、任务名称、日期时间（UTC + 本地）、任务类型（训练/巡逻/对抗/护航/对地/其他）
- 起降基地、简报文本、战役归属
- **归并元数据**：ACMI 录制时间窗、出现的呼号集合、归并确认状态
- 汇总：参战人数、**任务时长**（只算一次）、**飞行员累计**（人次）、战果/战损
- 公开开关（`public` 战报精选 vs `members` 完整日志）

> **两个时长口径**（多人同飞时必然不等，不是数据错误）：
>
> | 口径 | 算法 | 用途 |
> |---|---|---|
> | **任务时长** | 各架次在空区间的**并集** —— 同一段时间只计一次 | "这个任务占用了多久" |
> | **飞行员累计** | 各架次时长**相加**（人次） | "大家一共飞了多少"  |
>
> 实测：4 人同飞 → 任务时长 `1小时13分`，飞行员累计 `4小时24分`。
> 任务时长在**读取时**计算（`services/stats.py::mission_flight_seconds`），
> 不只依赖 `missions.duration_seconds` 冗余列 —— 后者只在归并时刷新。
> 架次未记录降落时用「起飞 + 在空时长」估区间终点，避免该架次整段丢失。

### 4.4 Sortie 个人架次
- 归属 Mission + 归属 Member（**通过呼号映射**）
- 机型、起飞/降落时间、飞行时长、起降次数、航程
- 武器投放明细、击落、被击落/战损
- 超限与事故标记（过载/超速/撞地/坠毁）
- 数据来源：`acmi` / `manual`
- **ACMI 原始飞行员名**（用于审计映射是否正确）

### 4.5 AC M I 导入实体
- `AcmiFile`：原文件存储、SHA256、上传人、上传时间、解析状态、录制时间窗、场景名
- `AcmiActor`：文件内的飞行员/单位条目，含原始名称
- `PilotMapping`：`AcmiActor 原始名` → `Member` 的映射（可复用的别名表）
- `ImportBatch`：一次归并建议（含 N 个文件 → 1 个 Mission），状态：待确认/已确认/已拒绝

### 4.6 其他实体
- `Qualification` 资质记录、`Award` 荣誉/勋章、`Event` 活动与报名、
  `Announcement` 公告、`ForumThread/Post` 论坛帖、`Document` 资料文件、
  `AuditLog` 操作审计、`Rank` 军衔定义、`Application` 招新申请

### 4.7 入队流水线 ✅（招新 + 注册审批合并为一条）

> 用户同时选择了"自助注册+审批"与"招新申请表单"。为避免两套流程割裂，
> **合并为一条流水线**，招新只是这条流水线的对外入口。

```
访客提交招新申请（呼号意向、飞行经历、时区、意向机型）
      │  状态：submitted
      ▼
管理员初审（可通过 / 拒绝 / 请求补充信息）
      │  状态：screening → approved / rejected
      ▼
发放注册邀请（一次性链接 / 邀请码，带有效期）
      │
      ▼
申请人自助注册（设置密码、确认呼号）
      │  账号状态：pending（预备）→ 仅能看 public 内容
      ▼
管理员正式激活 + 分配军衔 / 角色
      │  账号状态：active → 可看 members 内容
      ▼
入队记录写入 Member 变动历史
```

设计要点：
- 呼号**唯一性在申请阶段就要校验**（防止重名抢占）
- `pending` 账号能看到公开内容，但看不到内部日志 —— 复用了 §2 的可见性机制，无需额外逻辑
- 拒绝的申请保留记录（防止重复骚扰），但不进名册
- **激活后仍需上传一次 Logbook 与 Tacview**，才能建立"名册成员 ↔ 游戏内身份"的绑定

## 4.8 军衔与资质来源 ✅（本轮重要修正）

用户指出：**BMS 的 Logbook 自带军衔**。因此军衔与资质不再是纯手工维护，而是**有权威数据源**。

### 双源职责划分

| 数据 | 权威来源 | 说明 |
|---|---|---|
| 军衔 Rank | **BMS Logbook**（口径来源） | 游戏内随战绩/时长推进，是本联队的真实口径 |
| 资质 Qualification（空对空 / 空对地等级） | **BMS Logbook**（口径来源） | 游戏内 qualification 字段 |
| 累计飞行时长 / 累计架次 | **BMS Logbook**（口径来源） | 跨存档的历史总量 |
| 单场任务明细（武器、战损、轨迹） | **Tacview ACMI** | Logbook 不记录这些细节 |
| 呼号映射、账号绑定 | 网站内部 | 两边都要靠它才能对上人 |

> ⚠️ **重要修正（见 §8.1）**：`.lbk` 是强混淆二进制，**一期不自动解析**。
> 因此上表"来源"应理解为**权威口径**，实际录入方式为
> **管理员后台手工录入 + 成员自填审核**。功能完全一致，只是数据获取方式不同。

### 冲突消解规则（必须明确，否则统计会被污染）

```
Logbook 导入的军衔/资质/累计时长  →  标记为「游戏来源」
管理员手工修改的值               →  标记为「人工覆盖」，优先显示
```
- 每条数值都记录**来源**与**最后更新时间**
- 人工覆盖后，再次导入 Logbook **不自动覆盖**，而是提示"与游戏数据不一致，是否更新？"
- ⚠️ R8 由此升级：**同一指标存在两个来源，必须有明确优先级与冲突提示**，否则成员会质疑数据

### ❓ 待定：Logbook 是否可自动导入（Q10）
- 若能拿到结构化文件 → 资质与军衔可自动获取，手工录入降级为兜底
- 若只能人工抄录 → 保留手工录入界面（但工作量落在管理员身上）

## 5. ACMI 处理流程 ✅（核心流程）

```
上传 ACMI（成员自己 / 管理员批量）
      │
      ├─ 校验：格式、大小、SHA256 去重（防止重复上传同一文件）
      ├─ 存储原件（不入库，落文件系统 + 路径索引）
      ▼
解析（后台任务，进度可见）
      ├─ 读头部：录制起止时间、场景名、Tacview 版本
      ├─ 提取 Actor 列表（呼号 / PilotName / 机型 / 阵营）
      ├─ 提取事件流：武器投放、击毁、坠毁、超限
      └─ 累计航程（由位置变化计算，**仅出数值，不保留轨迹点** —— 见 §1.2）
      ▼
归并建议引擎
      ├─ 规则：录制时间窗重叠 + 呼号集合重合度 + 阵营一致
      └─ 输出：建议分组（可能 1 文件 = 1 任务，也可能 8 文件 = 1 任务）
      ▼
【人工确认页】★ 关键交互
      ├─ 每份文件选择：并入哪个 Mission / 新建 Mission / 忽略
      ├─ 合并、拆分、改归属；冲突与重合度可视化提示
      ▼
呼号映射
      ├─ 自动套用已有别名表
      ├─ 未识别的原始名 → 列出"未认领飞行员"，指派给 Member 或标记为"外部/敌方"
      ▼
生成 Sortie 记录 → 写入统计 → 归档原件
```

### 5.0 入口形态：ACMI 工作台 ✅（已实现，联队定稿）

**不设独立的 ACMI 上传页面。** 上面那条流程以「ACMI 工作台」的形式，
作为一个可折叠区块内嵌在三个业务页面里，并继承宿主页面的上下文：

| 宿主页面 | 战役 | 任务类型 | 归并结果 |
|---|---|---|---|
| `/theater/{id}` 战役管理 · 战役详情 | 固定为当前战役 | 可选 | 任务 `campaign_id` **直接写入当前战役** |
| `/log/campaign` 飞行记录 · 战役记录 | 锁定为页面顶部的战役筛选 | 可选 | 筛到哪个战役就归入哪个 |
| `/log/training` 飞行记录 · 训练记录 | 无（日常训练） | 锁定 `training` | 必然出现在训练记录列表里 |

区块内仍是三步：**上传文件 → 认领飞行员 → 归并确认**，阶段间用步骤条跳转；

## 5.2 ACMI 格式实地勘察结论 ✅（2026 实测，非推测）

> ⚠️ **范围说明**：本节及以下技术结论来自对现有 193 份历史 ACMI 的**只读分析**。
> 这些历史文件**不导入、不统计**（见 §5.3）。分析目的仅为**摸清格式与判定阈值**，
> 使线上处理新上传文件时一次正确。

对 `G:\BMS\Falcon BMS 4.38\User\Acmi\` 实际取样分析结果。

### 容器格式：**ZIP 包着一个文本文件**
```
2026-08-04_10-27-51.zip.acmi        ← 扩展名像 acmi，实际是 ZIP
  └─ acmi.txt  (50,847 bytes)       ← 唯一成员，纯文本
```
- ⚠️ **解析器必须"先当 ZIP 尝试解压，失败再当裸文本读"**，两种形态都存在

### 文本格式：Tacview ACMI 2.1 —— **可读、易解析** ✅
```
FileType=text/acmi/tacview
FileVersion=2.1
0,DataRecorder=Falcon BMS 4.38.1
0,DataSource=Falcon 4.0
0,ReferenceTime=2024-8-16T00:00:00Z
9,T=26.409252|40.544404|579.12|0|3.9|124.6|631334.5|795291.49|117.6,
   AOA=3.9,CAS=174,CallSign=Tiger41,Coalition=Hellas,Color=Blue,
   Health=1,IAS=174,Mach=0.53,Name=F-16C B52M HAF,Pilot=Oblivion,Type=Air+FixedWing
#24488.051
9,T=26.409512|40.544285|579.21||4.2||631356.72|795278.59|,FuelWeight=5195,LockedTarget=0
```

| 发现 | 含义 |
|---|---|
| **`Pilot=Oblivion` 直接写在对象属性里** | ✅ **R3 风险大幅降低** —— ACMI 自带飞行员名，不必靠猜 |
| `CallSign=Tiger41` 是独立字段 | 战术呼号 ≠ 飞行员名，两者要分别处理 |
| `Name=F-16C B52M HAF` | 机型可解析，但含涂装/型号后缀，需归一化 |
| `#24488.051` 为时间戳行 | 其余行是**增量差分**（只写变化字段）→ 解析器需维护**对象状态机**，不是逐行独立记录 |
| 对象编号混用十进制与十六进制（`9`、`a`） | ⚠️ 解析陷阱：对象 ID 要按 **16 进制**解析 |
| `Health` / `Mach` / `FuelWeight` / `LockedTarget` | 战损、超限、交战的原始依据齐全 |

### 真实数据量级（决定性能设计）
```
文件数：197 个        总大小：1301 MB
最大单文件：约 21 MB   最小单文件：6.6 KB
```
- ⚠️ **R1 已消除**（用户决定不做回放）：单文件 21 MB、帧率极高（50 KB 文本含 2 万多个时间戳），
  这仍然意味着**解析器必须高效**（流式逐行处理，不可整文件载入内存后逐条正则匹配），
  但**不再需要任何为"播放"服务的降采样或切片设计**。
- ⚠️ 上传环节必须支持 **20 MB 以上文件**，需设置上传体积上限与超时策略。

### 时间来源 ✅（含一处已修的严重解析错误）

实测 ACMI 文件名时间为 UTC（`10-27-51`），而 BMS 自身日志为东八区（同一时刻记录为 `18:20:10`）。
若此规律成立，则**文件名可直接作为任务时间来源**；
而 `ReferenceTime` 是剧本地图纪元时间（`2024-8-16`），**绝不能当作真实日期使用**。

**三个时间量的正确关系**（`⚠️` 标注的是曾经的错误实现）：

```
                    文件名时间（= 录制终点，实测验证过：与末标记推导出的终点一字不差）
                         ▲
                         │
   t=0 基准点 ───────────┼───────── 录制起点 ───────── 录制终点
   （剧本纪元）           │          基准+首标记        基准+末标记
                         │
   首标记 常是个大数 ─────┘   末标记
   （实测 36000.2 = 10 小时）
```

| 量 | 定义 | 曾经错写成 |
|---|---|---|
| `min_relative_seconds` | 文件内**最小**时间标记 | **根本没记录** |
| `max_relative_seconds` | 文件内**最大**时间标记 | 正确 |
| **`duration_seconds`** | `max − min` | ⚠️ 取了 `max` 本身 |
| `recorded_start_at` | t=0 基准 + **首**标记 | ⚠️ 写成 t=0 基准点本身 |
| `recorded_end_at` | t=0 基准 + 末标记 | 正确 |

**为什么错得这么离谱**：BMS 的 ACMI 时间戳以**剧本纪元**（`ReferenceTime`）为基点，
不是以录制起点为基点，所以首个标记往往是个大数。用「末标记」当时长，
等于把整段战役已经过去的时间都算进这一次录制里。

**实测影响**（真实文件，非构造样本）：

| 文件 | 真实录制时长 | 旧算法报出 | 多报 |
|---|---|---|---|
| `2026-01-02_15-26-30.zip.acmi` | 4.5 秒 | 36004.7 秒 | 36000 秒（≈10 小时） |
| `2026-01-11_17-51-53.zip.acmi` | 2.8 秒 | 10802.9 秒 | 10800 秒（≈3 小时） |
| **联队实际上传的 `2026-08-08_14-16-23.zip.acmi`** | **1 小时 13 分** | **51 小时 31 分** | 50 小时 |

波及面（都已修正）：
* 归并页的「时长」列；
* 任务列表的「总时长」列与任务详情的「历时」；
* 「录制时间窗」的**宽度**（起点曾被推到剧本纪元，窗口比真实录制宽出整个首标记）；
* 解析器的「时长超阈值」告警 —— 会被这个错误**误触发**，任何首标记不为 0 的
  文件都会莫名其妙报超时。

**未受影响**：架次级飞行时长按采样间隔累加（`flight += delta_t`），
本就是时间段之和，因此一直是正确的；`/log/campaign`、`/log/training` 用的是
架次之和，也没受污染。

**为什么测试没抓到**：测试的合成 ACMI 从 `#0.0` 开始，`min == 0`，
于是「时长 = 末标记」这个错误**完全看不出来**。现已补两条防线：
合成用例加上「标记不从 0 开始」的变体（`tests/acmi_parser_selfcheck.py` 的
`[1b]` 段），以及摄入链路的**不变量断言**「时间窗宽度 == 录制时长」
（`tests/ingest_selfcheck.py`）。

**老数据修正**：`scripts/reparse_acmi.py` 重解析原始文件并回填
（默认只预览，`--apply` 才写库）。由于 `min_relative_seconds` 无法从库里反推，
必须重解析 —— 原始 ACMI 都留在 `var/storage`，所以可重算。

## 7. 技术选型（部署环境由本方案决定）

用户未指定部署环境，因此**选型约束是"开发机 Windows + 部署可迁移"**，不绑定单一平台。

### 7.1 架构

| 项 | 建议 | 理由 |
|---|---|---|
| 架构 | **单体 Web 应用**（服务端渲染或前后端分离皆可） | <100 人规模，微服务是自找麻烦 |
| 数据库 | SQLite（开启 WAL 模式） | 已确认基线 |
| 数据访问 | 经 **ORM/查询构造器** 抽象，禁用 SQLite 专有语法 | 未来可平滑迁 PostgreSQL，且迁移动因很可能是"分析查询变慢" |
| 文件存储 | 本地文件系统 + 数据库存路径与 SHA256 | ACMI 与手册文件不入库 |
| 后台任务 | **必需的简单任务队列**（进程内队列或独立 worker） | ACMI 解析是耗时操作，不能阻塞 Web 请求 |
| 时区 | **数据库统一存 UTC**，展示按配置时区转换 | 虚拟联队常有跨时区成员，事后补录时区混乱会污染统计 |

### 7.2 语言/框架的取舍（待定 Q4-b）

| 方案 | 优势 | 劣势 | 适配度 |
|---|---|---|---|
| **Python**（FastAPI/Django） | ACMI 解析、数据分析生态最强；后续做轨迹处理/统计最省力 | 部署需装运行时（可用容器缓解） | ⭐ **已选定** |
| **Node.js**（NestJS/Next.js） | 前后端同一语言；部署轻 | 二进制文件解析与科学计算生态弱一些 | 未采用 |
| **Go** | 单二进制部署最省心，性能好 | 解析 ACMI、做数据分析的库少，开发速度慢 | 未采用 |

> ✅ **决策（v0.6）**：**Python + 单体应用 + SQLite + 简单任务队列**。
> 理由：用户授权按"最好维护"选择；本项目技术核心是**文件解析与统计分析**，
> Python 在此方向的库最成熟、容错处理成本最低。
> 维护性优势：单进程、单数据库、依赖少、可整体备份，一人可长期维护。
>
> 💡 具体框架倾向 **FastAPI（后端）+ 服务端渲染模板**：
> 一期不做前后端分离，避免同时维护两套代码与两套构建流程 —— 这是"最好维护"的关键取舍。

### 8.1 Q10 结论：Logbook 自动导入**降级为可选优化，不阻塞开发**

**实地勘察事实**（非推测）：
```
G:\BMS\Falcon BMS 4.38\User\Config\
    Oblivion.lbk    372 字节     ← 一个呼号一个文件
    Obsequies.lbk   372 字节
    Viper.lbk       372 字节
    SZSZS.lbk       372 字节
```
- ✅ **一个 `.lbk` 对应一个飞行员** —— 若将来要导入，无需拆分多人存档
- ⚠️ **强混淆二进制**：372 字节内容经异或分析**未解出可读明文**
  （早期"疑似解出 Callsign"的观察已被 `Format-Hex` 复核**证伪**，特此更正）
- ⚠️ 官方查看/编辑工具是 `Tools\Logbook Editor\LogbookEditor.exe`
  —— **2012 年构建的 Qt4 GUI 程序，是给人点的，无法在服务器上自动化调用**

**本方案的决定：**

| 方案 | 评估 | 结论 |
|---|---|---|
| A. 逆向 `.lbk` 格式自行解析 | 无公开文档；BMS 大版本更新可能改格式致解析器失效 | ❌ 不作为一期依赖 |
| B. 管理员后台**手工录入**军衔/资质/累计时长 | <100 人，每人几个字段，年录入量极小 | ✅ **采纳为正式方案** |
| C. 成员个人资料页**自助填写** + 管理员审核 | 省人力，但需防虚报 | ✅ 采纳为补充 |
| D. 用 LogbookEditor 人工读出后录入 | 繁琐，作兜底 | 🔶 备选 |

**对前序结论的修正：**
- §4.8 "以 Logbook 为权威来源" 应表述为：
  → **"以 Logbook 为权威口径，但通过人工录入/成员自填维护，不依赖自动解析"**
- §4.8 的**双源冲突消解规则依然有效**（每项数值标注来源与更新时间），继续沿用

**风险变化：**
- ✅ 项目**不再依赖任何私有文件格式** —— ACMI 是公开文本格式且稳定，
  BMS 升级不会打断导入链路（这是把 Logbook 降级换来的最大收益）
- ⚠️ **新增 R12**：人工录入的军衔/资质可能与游戏内实际值不一致
  → 缓解：显示"最后更新时间 + 录入人"，并提供**年度核对**提醒

**若后续仍想自动化**：应逆向 `LogbookEditor.exe`（它是读取 `.lbk` 的官方实现，
分析它比分析数据文件可靠得多）。**但此事不阻塞一期开发。**
